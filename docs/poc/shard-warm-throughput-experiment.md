# 追加検証 — オープンシャード数 S は warm write throughput で決まるか（負荷・データ量は寄与するか）

実施日: 2026-10-02（JST） / リージョン: us-west-2（オレゴン） / アカウント: <ACCOUNT_ID>

[verification-results.md](verification-results.md) の論点 **3.2（事前ウォームはシャードを増やす）**
を直接更新する独立実験の記録。本線の問い（軸 B4「壁が Lambda 同時実行枠へ移る」= `S × P ≥ 1,000`
に必要な `S ≥ 100`）に到達できるかの可能性探索を兼ねる。

---

## 0. 背景と問い

verification-results.md までで確定していたのは次の対応だった。

- warm write **4,000 → S = 4**、warm write **40,000 → S = 64**
- 導出下限 `warm write ÷ 1,000` は 40 だが、実測 S = 64 は **下限の 1.60 倍**

この 1.60 倍（上振れ）の出どころが未分離だった。記事 3 執筆中に生じた疑問として、
上振れ要因を次の 3 仮説に切り分けた。

- **H1: 負荷履歴による下駄** — 過去にかけた高負荷でパーティションが分割され、
  その分割は不可逆に積み上がって S を押し上げている
- **H2: データ量（項目サイズ・件数）起因** — テーブルに載っているデータ量が S を規定している
- **H3: warm 設定からの内部割当** — warm write を設定しただけで、負荷・データと無関係に
  内部的に S が決まる

事前の寄与見立ては **H1 > H3 > H2**。本実験はこれを実測で切り分ける。

### 本線の狙い（1,000 多重）

`S = 64 × P = 10 = 640` 多重までは warm 経由で到達が見えていた。Lambda 同時実行枠 1,000 に
壁を移す（B4）には `S ≥ 100` が要る。そこで問いを次に定めた。

> **warm 単独では 40,000 → S = 64 で頭打ちなのか。負荷でこれを 2 倍・3 倍に積み増せないか。**

積み増せれば「手立て X（負荷由来の分割を warm 由来の 64 に上乗せ）」が成立し、
クォータ引き上げ申請なしで 1,000 多重に手が届く。

## 1. 実験環境（使い捨て専用テーブル）

sandbox のアプリ構成には一切触れず、CLI で単発作成した検証専用テーブルを使った。

| 項目 | 値 |
|---|---|
| テーブル名 | `shard-probe-e1` |
| 課金モード | PAY_PER_REQUEST（オンデマンド） |
| キースキーマ | `pk`（S, HASH）のみ。GSI なし |
| Streams | 有効（NEW_AND_OLD_IMAGES） |
| 作成直後の warm | write 4,000 / read 12,000（オンデマンド既定） |

warm は**不可逆**（下げられない）ため、検証後に削除する前提。計測は
`DescribeStream` のページング込みで「オープンシャード（`EndingSequenceNumber == null`）」を数えた。
`WarmThroughput.Status` が **ACTIVE** になるまで S を確定しない（UPDATING 中は推移する）。

ツール（使い捨て。`tmp/shard-probe/`、git 管理外）:

- `count-shards.mjs` — オープンシャード S を計数（ページング + warm Status 併記）
- `e2-burst.mjs` — 乱数プレフィックス + ULID でキーを全空間に分散し BatchWriteItem を多並列投入
- `overload.mjs` — `e2-burst` を `child_process.fork` で複数プロセス並列化（単一プロセスの上限突破用）

## 2. E1 — warm 単独の S（負荷ゼロ・データゼロ）

warm write を既定 4,000 から **40,000** に引き上げ、**投入ゼロのまま** S を確定した。

### 2.1 warm 引き上げの推移（実測）

`update-table --warm-throughput WriteUnitsPerSecond=40000` 送信後、`Status = UPDATING` の間は
WriteUnitsPerSecond 表示が 4000 → **12000（中間値を経由）** → 40000 と段階的に上がり、
約 10 分前後で `Status = ACTIVE` に到達した。中間値 12000 を経由した事実は、warm が
一括ではなく**段階的に内部プロビジョニング**されていることを示す。

ACTIVE 到達の直後と +180 秒で計数し、いずれも同値で安定を確認した。

| 時点 | warm write | Status | SizeBytes | ItemCount | **OPEN_SHARDS** | TOTAL_SHARDS |
|---|---:|---|---:|---:|---:|---:|
| ACTIVE 直後 | 40,000 | ACTIVE | 0 | 0 | **64** | 124 |
| +180 秒 | 40,000 | ACTIVE | 0 | 0 | **64** | 124 |

### 2.2 E1 の判定

> **🟢 warm 40,000 → S = 64 は決定論的。負荷履歴ゼロ・データゼロでも 64 に到達する。**

- 事前の分岐基準は「S ≈ 40 なら旧スタックの 64 は負荷履歴の下駄（H1）、S ≈ 64 なら warm 単独（H3）」。
  **結果は後者（S = 64）。**
- したがって「1.60 倍の上振れ」という理解は誤りで、**S = 64 は warm 40,000 に対する
  決定論的な対応値**。旧スタック（`kiro-roasters-orders-38908186`）が 0 件でも S = 64 を
  維持していた既測事実とも整合する。
- **H1（負荷履歴の下駄）はこのケースでは効いていない。主因は H3（warm 設定からの内部割当）。**

## 3. E2 — 負荷で S を 64 から積み増せるか

同じ `shard-probe-e1`（warm 40,000 ACTIVE）に対し、投入前基準 S = 64 を確認してから
段階的に負荷を上げ、各投入後に時間をあけて S を再計数した。

### 3.1 投入レートと結果の一覧（実測）

| 段 | 投入方法 | 件数 | 実効レート（概算） | warm 比 | 投入後 S（最大 ~10 分観測） |
|---|---|---:|---:|---|---:|
| E2 軽め | 単一プロセス 3R×5万 | 15 万 | ~6,000/s ≈ 6MB/s | **warm 内** | **64**（変化なし） |
| E2 強め | 単一プロセス 10R×10万 | 100 万 | ~8,000/s ≈ 8MB/s | **warm 内** | **64**（変化なし） |
| E2 過負荷 | **8 プロセス** fork 2R×15万 | 240 万 | **~48,000/s ≈ 48MB/s** | **warm 超え** | **64**（変化なし） |

- 単一 Node プロセスは並列度を上げても **~8MB/s で頭打ち**（SDK/イベントループ側の上限）。
  warm 40,000（≈ 40MB/s 相当）を超えられず、過負荷状態を作れなかった。
- `child_process.fork` で **8 プロセス並列**にして初めて合算 **~48MB/s** に到達し、
  **warm を明確に超過**。ラウンド 2 で各プロセスのレートが低下（スロットリング +
  SDK リトライによる実効レート低下）し、**過負荷が実際に発生したことを確認**した。

### 3.2 全投入後のテーブル状態（実測）

全段投入（合計 **355 万件 ≈ 3.6GB**）の後、メタ集計が更新された状態で計数した。

| 項目 | 値 |
|---|---:|
| ItemCount | 3,550,000 |
| SizeBytes | 約 3,599,663,288（≈ 3.6GB） |
| **OPEN_SHARDS** | **64**（不変） |
| TOTAL_SHARDS | 124 → **188** に増加 |

> **解釈:** TOTAL（シャード系図の総数）は増えた＝分割・ローテーション自体は内部で起きている。
> しかし**同時にアクティブなオープンシャード S は 64 で張り付いた**。warm 維持のための
> 親→子ローテーション（クローズ→新規オープン）で TOTAL は伸びるが、
> **並列読み出し能力に相当するオープンシャード数は warm が規定する 64 のまま**、と読める。

### 3.3 E2 の判定

> **🔴 負荷では S は増えない。手立て X（負荷由来の分割を 64 に上乗せ）は成立しない。**

- warm 内の負荷（6〜8MB/s）はもちろん、**warm を超える過負荷（48MB/s、スロットリング実発生）**を
  継続しても、**3.6GB のデータを載せても**、オープンシャード S は 1 つも増えなかった。
- **オープンシャード S を動かすレバーは warm write throughput ただ一つ。**
  負荷・過負荷・データ量（項目数・サイズ）は S に寄与しない（H1・H2 を実測で否定）。

## 4. 本線（Lambda 1,000 多重 = S ≥ 100）への結論

> **オンデマンド/warm 経路では、現行クォータ（warm テーブル上限 40,000）の下で
> S = 64 が壁。`S × P` = 640 多重が上限で、S ≥ 100（= 1,000 多重）には到達できない。**

- 1,000 多重の**正攻法は warm write のテーブルクォータ（`L-AB614373` = 40,000）の引き上げ申請**のみ。
  当初「方針外」としていた道だが、実測の結果、1,000 狙いにはこれが唯一の正攻法と確定した。
  > **【E6 で更新】真の律速は基表 warm `L-AB614373` ではなく Streams write クォータ
  > `L-923BEB7A`（= 40,000）だった（§6-E）。Stream 有効テーブルではオンデマンド/プロビジョンド
  > いずれも 40,000 が壁。引き上げ申請の対象は `L-923BEB7A` である。**
- 線形仮定（40,000 → 64 ≒ **625 write/シャード**）が引き上げ後も成り立つなら、
  - S = 100 には warm ≈ **62,500**
  - `S × P` = 1,000（S = 100, P = 10）到達には warm **64,000 前後**
  という見積りになる。**ただしクォータ引き上げ後も線形が続くことは本実験では未確認**
  （申請・承認が必要なため）。確定しているのは「40,000 → 64、負荷では増えない」まで。

## 5. 未確認・限界（正確な線引き）

- **クォータ超えの warm（> 40,000）での S** は未測定。線形（625 write/シャード）が
  その先も続くかは未確認。
- 本実験の過負荷は **48MB/s / 数十秒**。これより桁違いに長時間・高レートな過負荷での
  挙動は見ていない（ただし「負荷では増えない」結論を覆す兆候は一切出ていない）。
- **warm の単位が WCU ベースか write ops ベースか未分離。** 投入項目を ~1KB 固定にしたため、
  1 write ≒ 1 WCU の世界しか見ていない（§6-A）。
- GSI あり・大型項目・複合キーなど**別のテーブル形状では未検証**（§6 の考察参照）。

## 6. 考察 — 「1.6 倍の関係式」はどこまで普遍か（オープン論点）

ユーザー問い:「0 件からシャード数が上がる＝オンデマンドなら、項目の大小や GSI 等の設定に
関係なく 1.6 倍の関係式が成り立ちそうか？」

本実験が**実証した範囲**は限定的である。正確には次まで。

- **単一ハッシュキー・GSI なし・PAY_PER_REQUEST** のテーブルで、
  **warm write 4,000 → S = 4** と **warm write 40,000 → S = 64** の 2 点。
- どちらも `warm write ÷ 1,000`（下限）に対し **×1.6**。
  2 点とも同じ係数 1.6 なので、**この形状では線形（625 write/シャード）が強く示唆**される。
- S は**負荷・過負荷（48MB/s）・データ量（3.6GB）に不追従**（H1・H2 を否定）。

ただし「種別に依らず普遍」とまでは本実験からは言えない。未分離の論点を 2 つに整理する。

### 6-A. warm の単位は WCU か write ops か（1 レコード > 1 WCU の扱い）

**WCU の定義:** 書き込み 1 回あたり **1KB までが 1 WCU**、超過分は 1KB ごとに +1 WCU（切り上げ）。
- 1KB 項目 → 1 write = 1 WCU
- 2KB 項目 → 1 write = 2 WCU
- 400KB 項目（最大）→ 1 write = 400 WCU

**本実験は項目を ~1KB 固定で投入したため、1 write ≒ 1 WCU の世界しか見ていない。**
したがって「625 write/shard」と「625 WCU/shard」を**区別できていない**。
これが分かれると S の決まり方が変わりうる。

- warm が **WCU ベース**なら: 大型項目（1 write > 1 WCU）では同じ write ops 数でも消費 WCU が
  増え、warm 40,000 WCU はより少ない ops で埋まる。**同じ warm 設定でも項目サイズで S の出方が
  変わる**可能性がある。
- warm が **write ops ベース**なら: 項目サイズによらず 625 ops/shard。サイズ非依存。

> **ユーザー仮説（「1 レコードあたり WCU が 1 を超えるケースは違いが出るかも」）は、まさにこの
> WCU ベース仮説に相当する。** 本実験の「3.6GB 載っても S 不変」は _データ総量_ 非依存の傍証には
> なるが、_1 write あたりの WCU_ を変えた比較ではないので、6-A の決着にはならない。

**切り分け実験（E5 改）:** 同一 warm（例 40,000）で項目サイズを 1KB / 4KB / 64KB / 400KB と振り、
S が不変（→ ops ベース）か、サイズに応じて縮む（→ WCU ベース）かを見る。

### 6-B. GSI は基表の S に加算されるか（独立シャード予想）

**ユーザー予想:**「GSI はそっち用のシャードが同じように増えるだけで、基表の総数は変わらない。」

これは理屈として筋が通る。

- GSI は実質「裏の追加テーブル」で、**独自の warm とパーティション**を持つ。
- 基表の DynamoDB Stream に出るのは**基表の変更のみ**で、GSI の更新は基表シャードに乗らない。
- よって **基表の S は基表 warm だけで決まり、GSI 側は GSI 側で別途シャードを持つ（基表 S に
  加算されない）** という予想になる。= 「基表 S は GSI 構成に不変」。

ただし 6-A と絡む分岐が 1 つある。GSI を足すと **基表 1 write あたりの消費 WCU が増える**
（基表書き込み + GSI 書き込み）。もし warm が WCU ベース（6-A）なら、GSI の存在が基表の実効
warm 消費を押し上げ、間接的に S に影響する経路もゼロではない。**ユーザー予想が正しい
（基表 S は GSI 不変）なら、それは「warm は基表と GSI で独立管理」= ops ベース寄りの傍証**にもなる。

**検証実験（E4）:** GSI を 1 本足したテーブルで、(1) 基表 S が GSI なしと同値か、
(2) GSI 側に別の S が立つか、を観測する。6-A（WCU か ops か）とも相互に効く。

### 6-C. その他の未確認

- **測定は 2 点のみ**（4,000 と 40,000）。同一係数でも線形の証明にはならない（中間点が要る → E3）。
- warm 内部アルゴリズムは AWS 非公開。引き上げ途中で 4000 → **12000** → 40000 と中間値を
  経由した以上、**単純な一次関数とは限らない**余地を残す。

> **現時点の最も確からしい言い方:**
> 「**単一キー・GSI なし・1KB 項目のオンデマンドテーブルでは、オープンシャード数 S は
> warm write throughput で決定論的に決まり（実測 2 点とも ÷1,000 の約 1.6 倍 = 625 write/shard）、
> 負荷・過負荷・データ総量には依存しない。** ただし _warm の単位が WCU か write ops か_（= 1 write
> が複数 WCU になる大型項目で S が変わるか）、_GSI が基表 S に効くか_、_クォータ超え領域_、
> _線形性（中間点）_ はいずれも未確認。」

### 普遍性を詰めるなら（次に取り得る実験）

- **E3:** 中間の warm（例 10,000 / 20,000）で S を測り、625 write/shard の線形を 3〜4 点で確認。
- **E4:** GSI を 1 本足し、基表 S が不変か・GSI 側に別 S が立つかを観測（6-B）。
- **E5 改:** 同一 warm で項目サイズを 1KB〜400KB に振り、S が ops ベース（不変）か
  WCU ベース（縮む）かを切り分け（6-A）。**本実験で最も優先度が高い論点。**

## 6-D. E5改（実測）— 項目サイズ（1 write あたり WCU）は S に効くか

§6-A の WCU/ops 論点に実測で決着をつけた。`shard-probe-e1`（1KB 項目）と**同一構成**
（単一キー pk・GSI なし・PAY_PER_REQUEST・Streams NEW_AND_OLD_IMAGES）の
使い捨てテーブル `shard-probe-e5` を作り、**項目サイズだけ 64KB（= 1 write 64 WCU）**に変えて比較した。

### 手順と実測

1. 作成直後 warm write 4,000（既定）→ **S = 4**（`shard-probe-e1` と同一の出発点）。
2. **warm 4,000 のまま 64KB 項目を投入** → ops レートが **約 61/s に張り付いた**。
   これは `4,000 WCU/s ÷ 64 WCU/write ≈ 62 write/s` と一致。
   **= warm が WCU ベースで ops を律速していることの直接観測。**
   （参考: 1KB 項目では同条件で約 6,000/s 出ていた。）
   この間もオープンシャードは **S = 4 のまま**。
3. warm を **40,000** に引き上げ（ACTIVE 到達。中間値は今回 **10,482** を経由。
   `shard-probe-e1` のときの 12,000 とは異なる中途半端な中間値だった）。
4. ACTIVE 直後と +150 秒で計数 → **両時点とも S = 64 / TOTAL = 124**。

| テーブル | 項目サイズ | 1 write の WCU | warm write | **OPEN_SHARDS** | TOTAL |
|---|---:|---:|---:|---:|---:|
| `shard-probe-e1` | ~1KB | 1 | 40,000 | **64** | 124 |
| `shard-probe-e5` | 64KB | 64 | 40,000 | **64** | 124 |

### 6-D の判定

> **🟢 項目サイズ（1 write あたり WCU）はオープンシャード数 S に独立しては効かない。
> S を決めるレバーは warm の WCU "設定値" ただ一つ。1KB でも 64KB でも warm 40,000 → S = 64。**

- ただし「warm は WCU で効く」こと自体は事実（手順 2 の ops 張り付き = 4,000 ÷ 64）。
  **大型項目は _ops レートの出方_ を絞るが、_オープンシャード数 S_ は変えない。**
- ユーザー仮説（「1 レコードあたり WCU が 1 を超えると違いが出るかも」）への回答:
  **違いが出るのは「同じ warm で捌ける ops 数」であって、「シャード数 S」ではない。**
- §6-B（GSI）への含意: S が warm WCU 設定値だけで決まるなら、GSI を足して基表 1 write の
  消費 WCU が増えても、warm の**設定値**が同じなら基表 S は不変、というユーザー予想を支持する方向。
  （GSI 側に別 S が立つかは E4 として未検証のまま。）

## 6-E. E6（実測）— プロビジョンドなら S を 40,000 超に増やせるか（1,000 多重の最有力ルート検証）

「オンデマンド warm は 40,000 で頭打ち。プロビジョンド WCU はアカウント上限 80,000（`L-34F8CCC8`）
なので、WCU 64,000〜80,000 を張れば S ≥ 100（= 1,000 多重）に届くのでは」という仮説を検証した。
`shard-probe-e1/e5` と同一構成（単一キー・GSI なし・Streams NEW_AND_OLD_IMAGES）で、
課金モードだけ **PROVISIONED** にした使い捨てテーブル `shard-probe-e6` を作成。
WCU 40,000 → 64,000 → 80,000 の 3 段で S を測る計画だった。

### 実測

| 段 | 設定 WCU | 結果 | OPEN_SHARDS |
|---|---:|---|---:|
| 1 | 40,000 | 作成 ACTIVE、+180s でも安定 | **41** |
| 2 | 64,000 | **ValidationException で拒否**（下記） | — |
| 3 | 80,000 | （2 で頭打ちのため未実施） | — |

**第 2 段の WCU 64,000（および 41,000 でも同様）でエラー:**

> `Requested write capacity units exceed current limit allowed for **stream-enabled tables**.`

= **Streams を有効にしたテーブルのプロビジョンド WCU 上限は 40,000**（クォータ `L-923BEB7A`
Streams write Provisioned = 40,000 に一致）。41,000 でも拒否されたので境界は 40,000 で確定。

### 6-E の判定（本線の結論を書き換える重要事実）

> **🔴 プロビジョンドに替えても S を 40,000 超に増やす道は塞がっている。真の律速は
> 基表 warm クォータ（`L-AB614373`）ではなく、Streams write クォータ（`L-923BEB7A` = 40,000）だった。**

- **モード間で係数が違う**: 同じ WriteCapacity 40,000 でも
  **プロビジョンド S = 41（下限 40 の約 1.0 倍）** / **オンデマンド warm S = 64（1.6 倍）**。
  プロビジョンドで WCU 40,000 を張ると `WarmThroughput` 表示も自動的に `40000w` になる
  （確保容量＝常時 warm 扱い）が、立つシャードは 41 で下限に張り付く。
- **1,000 多重を狙うならオンデマンド warm 40,000（S = 64）の方が有利。** プロビジョンドに
  替えると S は 64 → 41 に**減る**うえ、40,000 超も同じく不可。仮説（プロビジョンドで 80,000 →
  S ≥ 100）は**否定された**。
- **1,000 多重の唯一の正攻法は、Streams write プロビジョンドクォータ `L-923BEB7A`（40,000）の
  引き上げ申請。** これまで律速と見ていた基表 warm `L-AB614373`（40,000）ではなく、
  **Stream 有効時に効くのは Streams 側クォータ**だと判明した。
  （両者とも既定 40,000 で値が一致していたため、E6 まで切り分けられていなかった。）

### コスト実績

WCU 40,000（≈ $26/時）での稼働は数分で、第 2 段が即拒否されたため早期終了。
測定後ただちに WCU/RCU を 1 に下げ、テーブルを削除した。実課金は **$2〜3 程度**
（当初見積もり $40〜60 を大きく下回る）。
