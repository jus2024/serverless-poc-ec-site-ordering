# Requirements Document

EC 注文処理パイプライン PoC（ベース + Streams 直結構成）

## Introduction

Kiro Roasters（架空のスペシャルティコーヒー焙煎メーカー）の D2C EC における注文処理基盤を題材に、
**DynamoDB Streams と Lambda を直結したとき、限界がどこに来るのか**を実測する。

### 中心的な問い

バズによって入力が通常の 100 倍・1000 倍になったとき、何が起きるのか。

1. DynamoDB Streams の発行側が限界になるのか
2. Lambda の同時実行数が限界になるのか
3. 限界は段階的・連鎖的に現れるのか

この問いに答えるため、**壁の位置を絶対値で測り、壁を1つ外して次の壁を見に行く**という構成をとる。

### 事前分析から導いた仮説

Streams のオープンシャードはテーブルのパーティションと 1 対 1 で対応し、
Lambda は 1 シャードを 1 インスタンスで処理する。`ParallelizationFactor`（PF）が
シャードあたりの並行数を増やす。したがって:

```
最大同時実行数 = オープンシャード数(S) × PF(P)
最大処理能力   = S × P ÷ 1レコードの処理時間(D)
```

新規オンデマンドテーブルは初期状態で 4,000 writes/s を捌けることから S ≒ 4 と推定される。
D = 3.6 秒（決済 3 秒 + 通知 0.5 秒 + その他 0.1 秒）とすると:

| PF | 最大同時実行 | 処理能力 |
|----|------------|---------|
| 1 | 4 | 67 件/分 |
| 10 | 40 | 667 件/分 |

**予想される結論:** 壁は Lambda の同時実行枠（1,000）ではなく `S × P` である。
PF=10 でも同時実行は 40 で、枠の 4% にすぎない。
入力が 1000 倍になってもシャードは増えないため、**消費能力は 1 倍のまま**である。

これらはすべて実測で検証・反証する対象であり、確定した事実として扱わない。

### 検証の 2 つの軸

| 軸 | テーブルの状態 | 想定する現実 | 見に行く壁 |
|----|-------------|------------|-----------|
| A | 既定のオンデマンドテーブル（S ≒ 4） | 新しいテーブル、低トラフィックのテーブル | `S × P` の壁。滞留とデータロス |
| B | 事前ウォームでシャードを増やしたテーブル | 成熟したテーブル、バズに備えて事前ウォームしたテーブル | Lambda 同時実行枠の壁。同期パスへの巻き添え |

軸 B は作り物ではない。事前ウォーム（pre-warming）は AWS が
「10 倍・100 倍の計画的なピークに備える」機能として提供しているものであり、
かつ実運用で年月を経たテーブルは自然に多数のパーティションを持つ。
**軸 A と軸 B は「同じバズが、テーブルの成熟度によって違う壊れ方をする」ことを示す。**

## Glossary

| 用語 | 定義 |
|------|------|
| `direct` パイプライン | DynamoDB Streams を単一の Lambda に直結し、後続処理を直列実行する構成。本 Spec の対象 |
| `fanout` パイプライン | Streams をルーター Lambda で受け、SQS 経由で複数ワーカーに分配する構成。本 Spec のスコープ外 |
| 後続処理 | 注文作成をきっかけに走る 4 つの処理（決済・在庫引当・注文確認通知・ポイント付与） |
| 段階 | 後続処理 1 つ分の単位。`payment` / `allocation` / `notification` / `point` |
| オープンシャード | Streams のシャードのうち、まだ閉じていないもの。テーブルのパーティションと 1 対 1 で対応する |
| 並列化係数（PF） | Streams イベントソースマッピングの `ParallelizationFactor`。1 シャードあたりの並行バッチ数（既定 1、最大 10） |
| 消費能力 | 後続処理が単位時間に処理できる注文数。`S × P ÷ D` |
| 滞留（backlog） | ストリームに書かれたが未処理のレコード。投入が消費能力を超えると増加する |
| `IteratorAge` | Lambda が処理したレコードの、ストリームへの書き込みからの経過時間。滞留の指標 |
| データロス猶予時間 | 滞留が Streams の保持期限（24 時間）に達してレコードが失われるまでの残り時間 |
| 回復時間 | バズが終わった後、滞留を消化しきるまでの時間。`滞留 ÷ (消費能力 − 投入)` |
| 巻き添えスロットル | 後続処理が Lambda の同時実行枠を消費した結果、無関係な照会 API がスロットルされる現象 |
| 事前ウォーム | DynamoDB の warm throughput を引き上げ、テーブルが瞬時に捌ける容量を増やす操作 |
| 並行計測 | 負荷生成中に注文照会 API を連続呼び出しし、レイテンシとエラー率を測る検証操作 |
| 検証者 | この PoC を操作して計測する開発者。エンドユーザーは存在しない |

## 前提と読み替え

出典の要件定義は独立した CDK リポジトリを前提にしていた。本リポジトリは
Amplify Gen 2 の業務 Web アプリテンプレートであるため、以下を読み替える。

| # | 出典の記述 | 本 Spec での扱い | 理由 |
|---|-----------|----------------|------|
| 1 | 独立した `kiro-roasters-ec-stream` リポジトリ構成 | 既存テンプレート構成に合わせる。IaC は `amplify/custom/`、Lambda は `amplify/functions/`、フロントは `src/` | テンプレートの構成規約（`.kiro/steering/structure.md`）を維持する |
| 2 | NFR-5.4「検証シナリオの切り替えは CDK のコンテキストまたはスタックパラメータで行える」 | 環境変数で切り替える | `ampx sandbox` に `--context` が無く、`CDK_CONTEXT_JSON` も合成に届かないため、環境変数が唯一の経路 |
| 3 | FR-3.5「DynamoDB 編で作成済みの `kiro-roasters-inventory` を使用する」 | 本リポジトリ内に引当用テーブルを**新規に**作成する（別名） | 既存テーブルは別リポジトリが所有しており、跨いで参照すると独立デプロイできず NFR-4.1（一括削除）も崩れる |
| 4 | NFR-5.3「`npx cdk deploy` で完結」 | `npx ampx sandbox`（開発）/ Amplify Hosting（本番）に読み替える | Amplify Gen 2 バックエンドは内部で CDK を使うため NFR-5.1（CDK / TypeScript）は満たせる |
| 5 | NFR-4.3「負荷テスト時のコストが $10 以内」 | **$100 以内**に緩和する | 軸 B（シャードを増やして次の壁を見る）に予算を割く。使わなければ使わない |
| 6 | シナリオ D「800 件/分で Lambda 枠 1,000 に接近」 | 成立しないため差し替える | 事前分析のとおり、800 件/分では同時実行は約 40。壁の位置を絶対値で測る設計に変える |
| 7 | シナリオ E「巻き添えスロットル」 | 軸 B（シャードを増やした構成）で自然に到達させる | 軸 A では発生しない。発生しないことの実証も成果として扱う |

### 出典の要件のうち `direct` では満たせないもの

出典 FR-2.5「外部 API のレート制限（50 req/s 想定）を超えないよう流量制御する」は、
`direct` 構成では実現手段がない。後続処理が Streams 直結の 1 つの Lambda に閉じているため、
決済だけを個別に流量制御できないからである。

これは実装の不備ではなく `direct` 構成の構造的な限界であり、
**満たせないことを検証結果として記録する**（要件 9.6）。

なお `S × P` が同時実行の上限を作るため、`direct` 構成は
**意図せず流量制御されている**状態でもある。これは検証で確認する論点とする。

### その他の前提

- AWS アカウントが利用可能であること
- Lambda 同時実行枠がデフォルト 1,000 であること（引き上げ申請はしない）
- Node.js 22.x / npm がローカルにインストール済み
- 検証は開発者自身の sandbox 環境で行う。エンドユーザーに公開しない

### 基準値（通常時の注文量）について

出典は「月間約 500件（1〜2件/分）」と記載しているが、この 2 つは整合しない
（月間 500 件は約 0.012 件/分であり、1〜2 件/分は月間約 65,000 件に相当する）。

本 Spec は**倍率ではなく絶対レートで壁を測る**設計にすることで、この曖昧さを回避する。
壁の位置が絶対値で分かれば、任意の基準値に対して「何倍のバズで壁に届くか」は逆算できる。

### 注文テーブル `kiro-roasters-orders`

| 属性 | 型 | キー | 説明 |
|------|-----|------|------|
| `order_id` | String | PK | `ORD#{ULID}` 形式。時系列にソート可能な一意 ID |
| `customer_id` | String | SK | `CUST#{customer-id}` |
| `order_status` | String | — | 後述のステータス一覧 |
| `items` | List | — | `[{sku, qty, price}]` |
| `total_amount` | Number | — | 注文合計（税込） |
| `point_earned` | Number | — | 付与ポイント |
| `created_at` | String | — | ISO 8601 |
| `updated_at` | String | — | ISO 8601 |
| `stages_done` | Number | — | 完了した後続処理の数（0〜4） |
| `{stage}_status` | String | — | 段階ごとの結果。`stage` は `payment` / `allocation` / `notification` / `point` |
| `{stage}_at` | String | — | 段階ごとの完了時刻（ISO 8601） |
| `failure_reason` | String | — | 失敗理由（失敗時のみ） |
| `load_test_id` | String | — | 負荷テスト実行 ID（負荷生成時のみ） |
| `pipeline_mode` | String | — | この注文を処理した構成。本 Spec では常に `direct` |
| `expires_at` | Number | — | TTL（Unix timestamp） |

- StreamViewType: `NEW_AND_OLD_IMAGES`
- BillingMode: `PAY_PER_REQUEST`（オンデマンド）
- Warm throughput: 検証パラメータで指定可能（軸 B）
- GSI `customer-orders-index`: PK `customer_id` / SK `created_at`

**注文ステータス:**
`PENDING` / `PAID` / `ALLOCATED` / `NOTIFIED` / `COMPLETED` / `PAYMENT_FAILED` / `ALLOCATION_FAILED`

### 引当用在庫テーブル（新規・読み替え3）

引当処理で条件付き `UpdateItem` の対象にする。
キー設計は在庫管理編の Good Table を踏襲する（PK `itemId` / SK `warehouseId`）。
テーブル名は既存テーブルと衝突しない名前にする。

### 冪等性管理テーブル

Lambda Powertools Idempotency が使用する。TTL 付きで自動失効させる。

| 属性 | 型 | キー | 説明 |
|------|-----|------|------|
| `id` | String | PK | 冪等性キー |
| `status` | String | — | `INPROGRESS` / `COMPLETED` / `EXPIRED` |
| `data` | String | — | 前回の実行結果（JSON） |
| `expiration` | Number | — | TTL（Unix timestamp） |

### 実行管理テーブル

負荷生成と並行計測の実行状態・結果を記録する。
**実行時のシャード数と算出した消費能力も記録する**（要件 19）。

## Requirements

### 要件 1: 注文受付

**ユーザーストーリー:** 検証者として、注文を投入して後続処理を起動したい。それにより Streams 起点の処理フローを観測できる。

#### 受入基準

1. WHEN 注文受付 API に POST リクエストが送られる THEN システムは注文レコードを注文テーブルに書き込む（FR-1.1 / FR-1.2）
2. THE 注文レコード SHALL 注文 ID、顧客 ID、商品リスト、合計金額、ステータスを含む（FR-1.3）
3. WHEN 注文レコードが作成される THEN `order_status` の初期値は `PENDING` である（FR-1.4）
4. THE 注文 ID SHALL `ORD#{ULID}` 形式であり、生成順にソート可能である（新規）
5. WHEN リクエストで商品リストが指定されない THEN システムは商品マスタからランダムに注文明細を生成する（新規、FR-7.3 を満たすため）
6. WHEN リクエストで顧客 ID が指定されない THEN システムはテスト顧客 ID をランダムに割り当てる（新規）
7. THE 注文受付 API SHALL 後続処理の完了を待たずに応答を返す（新規、FR-1 の非同期前提）
8. WHEN 商品リストに商品マスタに存在しない SKU が含まれる THEN システムは 400 応答を返し、注文を作成しない（新規）
9. THE 合計金額 SHALL 明細の `qty × price` の総和である（新規）
10. THE 注文受付 API SHALL 自身の処理時間を応答に含める（新規、後続処理の負荷が受付側に波及していないかの判断材料）

### 要件 2: 注文ステータス照会

**ユーザーストーリー:** 検証者として、注文の処理状況を照会したい。それにより後続処理の負荷が照会系に波及しているかを判断できる。

#### 受入基準

1. WHEN 注文 ID を指定して照会 API に GET リクエストが送られる THEN システムは注文のステータスと段階ごとの進捗を返す（FR-6.1）
2. WHILE 後続処理が高負荷である THE 照会 API SHALL 成功応答を 500ms 以内に返す（FR-6.2）
3. WHEN 顧客 ID を指定して照会 API に GET リクエストが送られる THEN システムは GSI `customer-orders-index` を使って当該顧客の注文一覧を新しい順に返す（新規）
4. WHEN 存在しない注文 ID が指定される THEN システムは 404 応答を返す（新規）
5. THE 照会レスポンス SHALL 注文作成から各段階の完了までの経過時間を含む（新規、NFR-1.1 の計測に必要）
6. THE 照会レスポンス SHALL 全段階完了までの経過時間を含む（未完了なら null）（新規）
7. THE 照会 API SHALL 後続処理の Lambda とは別の Lambda 関数として実装される（FR-6.2 / 波及の観測に必要）
8. THE 照会 API SHALL 注文テーブルへの読み取り権限のみを持つ（新規、最小権限）

### 要件 3: 商品マスタ

**ユーザーストーリー:** 検証者として、生成される注文データが業務コンテキストと整合していてほしい。それにより検証結果を業務の言葉で説明できる。

#### 受入基準

1. THE 商品マスタ SHALL `docs/poc/kiro-roasters-background.md` の命名規則に従った SKU を持つ（FR-7.3）
2. THE SKU 形式 SHALL `ITEM#{産地略}-{品種略}-{グレード}-{焙煎度}-{容量}` である（FR-7.3）
3. THE 商品マスタ SHALL 産地・焙煎度・容量の組み合わせから生成され、EC 向け商品のみを含む（新規、業務用 5kg を除外する）
4. THE 各商品 SHALL SKU、商品名、税込単価を持つ（新規）
5. THE 商品マスタ SHALL Lambda とフロントエンドの双方から同じ内容を参照できる（新規）

### 要件 4: 決済処理

**ユーザーストーリー:** 検証者として、外部決済 API 呼び出しに相当する遅延を持つ後続処理が欲しい。それにより処理時間が消費能力に与える影響を観測できる。

#### 受入基準

1. WHEN 注文が受け付けられる THEN システムは決済処理を実行する（FR-2.1）
2. THE 決済処理 SHALL 外部決済 API の呼び出しを待機で擬似化する（スコープ外の定義に基づく）
3. THE 擬似待機時間 SHALL 設定で変更できる（消費能力の式の変数 D を動かすため）
4. WHEN 決済が成功する THEN システムは注文ステータスを `PAID` に更新する（FR-2.2）
5. WHEN 決済が失敗する THEN システムは注文ステータスを `PAYMENT_FAILED` に更新し、`failure_reason` を記録する（FR-2.3）
6. WHEN 決済が失敗する THEN システムは以降の段階（引当・通知・ポイント付与）を実行しない（新規、業務上の整合性）
7. WHEN 同一注文に対して決済処理が再実行される THEN システムは二重に課金せず、前回の結果を返す（FR-2.4）
8. THE 決済処理 SHALL 意図的に失敗させる手段を持つ（新規、FR-2.3 と DLQ の動作確認に必要）

### 要件 5: 在庫引当

**ユーザーストーリー:** 検証者として、DynamoDB への条件付き更新を伴う後続処理が欲しい。それにより在庫という業務制約が絡む処理の挙動を観測できる。

#### 受入基準

1. WHEN 決済が完了する THEN システムは注文商品の在庫を引当する（FR-3.1）
2. WHEN 引当が成功する THEN システムは注文ステータスを `ALLOCATED` に更新する（FR-3.2）
3. WHEN 在庫が不足している THEN システムは注文ステータスを `ALLOCATION_FAILED` に更新し、`failure_reason` を記録する（FR-3.3）
4. WHEN 同一注文に対して引当処理が再実行される THEN システムは二重に在庫を減算せず、前回の結果を返す（FR-3.4）
5. THE 引当処理 SHALL 引当用在庫テーブルに対する条件付き更新で在庫数を減算する（読み替え3 / FR-3.5）
6. IF 引当対象の在庫レコードが存在しない THEN システムは在庫不足と同じ扱いにする（新規）
7. THE 引当用在庫テーブル SHALL 初期在庫を投入する手段を持つ（新規、在庫ゼロだと引当が常に失敗し検証にならない）
8. WHEN 明細のうち一部の引当が成功し残りが失敗する THEN システムは在庫が部分的に減算された状態を残さない（新規）
9. THE 引当対象の倉庫 SHALL 単一の倉庫に固定する（新規、倉庫振り分けは検証の変数を増やすだけ）

### 要件 6: 注文確認通知

**ユーザーストーリー:** 検証者として、短時間で終わる後続処理が欲しい。それにより処理時間の異なる段階が混在したときの挙動を観測できる。

#### 受入基準

1. WHEN 決済と引当が完了する THEN システムは顧客に確認メールを送信する（FR-4.1）
2. THE 通知内容 SHALL 注文番号、商品名、合計金額、到着予定を含める（FR-4.2）
3. THE メール送信 SHALL 構造化ログの出力で代替する（スコープ外の定義に基づく）
4. WHEN 通知が完了する THEN システムは注文ステータスを `NOTIFIED` に更新する（FR-4.3）
5. WHEN 同一注文に対して通知処理が再実行される THEN システムは二重に送信せず、前回の結果を返す（FR-4.4）
6. THE 通知処理の擬似待機時間 SHALL 設定で変更できる（新規）
7. THE 商品名 SHALL 商品マスタから解決する（新規、注文レコードは SKU しか持たない）

### 要件 7: ポイント付与

**ユーザーストーリー:** 検証者として、注文完了を確定させる後続処理が欲しい。それにより全段階の完了までの経過時間を計測できる。

#### 受入基準

1. WHEN 決済が完了する THEN システムは購入金額の 1% をポイントとして付与する（FR-5.1）
2. THE 付与ポイント SHALL 円未満を切り捨てた整数である（新規）
3. WHEN 全ての後続処理が完了する THEN システムは注文ステータスを `COMPLETED` に更新する（FR-5.2 を要件 8 に合わせて調整）
4. WHEN 同一注文に対してポイント付与が再実行される THEN システムは二重に付与せず、前回の結果を返す（FR-5.3）
5. THE 付与ポイント SHALL 注文レコードの `point_earned` に記録される（データモデル定義）

### 要件 8: 段階ごとの進捗記録

**ユーザーストーリー:** 検証者として、どの段階がいつ終わったかを知りたい。それにより処理時間の内訳を分解して原因を特定できる。

#### 受入基準

1. THE 注文レコード SHALL 後続処理の段階ごとに、その段階の結果と完了時刻を独立した属性として保持する（新規）
2. THE 注文レコード SHALL 完了した段階数を保持する（新規）
3. WHEN 同一段階が二重に実行される THEN 完了した段階数は二重に加算されない（新規）
4. THE `COMPLETED` への遷移 SHALL 全 4 段階が完了したことを条件とする（新規）
5. THE ステータス遷移 SHALL `PENDING` → `PAID` → `ALLOCATED` → `NOTIFIED` → `COMPLETED` の順に進む（FR-2.2 / FR-3.2 / FR-4.3 / FR-5.2）
6. WHEN いずれかの段階が失敗する THEN 注文ステータスは対応する失敗ステータスになり、以降の段階は実行されない（要件 4.6 / 新規）

> **`COMPLETED` の条件を変更した理由:**
> 出典 FR-5.2 は「ポイント付与が成功したら `COMPLETED`」だが、
> 「ポイント付与が最後に終わる」という実行順への依存を要件に埋め込むことになる。
> `direct` の直列実行では偶然成立するが、意味としては「全段階完了」が正しい。

### 要件 9: direct パイプライン

**ユーザーストーリー:** 検証者として、Streams に Lambda を直結した構成の限界を測りたい。それにより非同期化の必要性を数字で示せる。

#### 受入基準

1. THE システム SHALL 注文テーブルの Streams を単一の Lambda に直結する
2. THE 当該 Lambda SHALL 決済、引当、通知、ポイント付与を直列に実行する
3. THE Streams イベントソースマッピングの並列化係数（PF）SHALL 設定で変更できる（消費能力の式の変数 P を動かすため）
4. THE システム SHALL 後続処理の負荷が注文照会 API に波及するかどうかを計測できる（要件 12。**波及の有無は実測で判定し、発生を前提にしない**）
5. THE 構成 SHALL Streams の `IteratorAge` を CloudWatch で観測できる
6. THE 検証記録 SHALL 出典 FR-2.5（決済の流量制御）が本構成では満たせないことと、`S × P` が意図せず流量制御として働いているかどうかを明記する
7. THE Streams のイベントソースマッピング SHALL 注文の新規作成（`INSERT`）のみを後続処理の対象にする（新規、後続処理自身の更新で再帰しないため）
8. THE Lambda SHALL バッチ内で失敗したレコードのみを再試行対象として報告する（NFR-2.3）
9. WHEN レコードの処理が繰り返し失敗する THEN システムは当該レコードを DLQ に退避する（NFR-2.2）

> **要件 9.7 が必要な理由:**
> 後続処理は注文レコードを 4 回更新するため、フィルタしないと
> processor が自分の更新で再起動され、1 周ごとに 4 倍で増幅する無限ループになる。

### 要件 10: 検証パラメータの切り替え

**ユーザーストーリー:** 検証者として、消費能力を決める 3 変数とテーブルの成熟度を切り替えたい。それにより壁の位置が何で決まるかを切り分けられる。

#### 受入基準

1. THE 並列化係数（P）SHALL 設定で変更できる（要件 9.3）
2. THE 各段階の擬似処理時間（D の構成要素）SHALL 設定で変更できる（要件 4.3 / 要件 6.6）
3. THE 注文テーブルの warm throughput SHALL 設定で指定できる（軸 B。S を動かすため）
4. THE 設定 SHALL 環境変数で与える（読み替え2）
5. WHEN 設定値が範囲外である THEN システムは既定値に黙って落ちるのではなく、合成を失敗させる（新規、どの条件で計測したか誤認しないため）
6. THE 現在有効な設定値 SHALL 実行時に確認できる（新規、計測条件と記録の突き合わせに必要）
7. THE 再デプロイが必要な設定と不要な設定 SHALL design で明示される（新規）
8. WHERE warm throughput を引き上げた THE システム SHALL その値を下げられないことを検証者に明示する（新規、AWS の仕様。取り返しがつかない操作）

### 要件 11: 負荷生成

**ユーザーストーリー:** 検証者として、バズ状態を再現したい。それにより通常時には現れない限界を観測できる。

#### 受入基準

1. WHEN 負荷生成を開始する THEN システムは指定された注文件数/分で注文を投入する（FR-7.1）
2. THE 負荷生成 SHALL 漸増 → ピーク → 漸減の負荷カーブをシミュレートできる（FR-7.2）
3. THE 負荷生成 SHALL 定常負荷（カーブなし）も選べる（新規、壁の位置の測定には定常が適する）
4. THE 生成される注文データ SHALL 商品マスタに基づく（FR-7.3）
5. THE 負荷生成 SHALL 実行 ID を発行し、投入した注文を後から集計できる（新規）
6. THE 負荷生成 SHALL 実行状態（投入件数、エラー件数、経過時間、実行条件）を照会できる（新規）
7. THE 負荷生成 SHALL 2 件/分から 16,000 件/分までの投入レートを達成できる（軸 A・軸 B の全シナリオ）
8. WHILE 負荷生成が動作している THE 検証者 SHALL 注文照会 API に並行してリクエストを送れる（要件 12）
9. THE 負荷生成 SHALL 開始要求に対して即座に応答し、投入は非同期に継続する（新規、API Gateway の 29 秒制限を超える継続時間に対応するため）
10. THE 負荷生成 SHALL 自身が計測対象の同時実行枠を過度に消費しない構成にする（新規、負荷生成が観測対象を歪めないため）
11. THE 負荷生成 SHALL 実際に達成した投入レートを記録する（新規、目標レートと実績の乖離があると全ての算出が狂う）

### 要件 12: 並行計測（同期パスへの波及の測定）

**ユーザーストーリー:** 検証者として、後続処理が高負荷なときの照会 API のレイテンシとエラー率を測りたい。それにより波及の有無を定量的に示せる。

#### 受入基準

1. WHEN 並行計測を実行する THEN システムは注文照会 API に連続してリクエストを送り、レイテンシとエラー率を計測する
2. THE 計測結果 SHALL スロットルエラー（429 / `TooManyRequestsException`）を他のエラーと区別して集計する
3. THE 計測結果 SHALL レイテンシの分布（p50 / p95 / p99 / 最大）を含む（新規、平均値だけでは波及が見えない）
4. THE 計測 SHALL 検証者のローカル環境の回線品質に影響されない場所で実行する（新規、測定の妥当性）
5. THE 計測結果 SHALL 実行条件（投入レート、処理時間、PF、シャード数）とともに記録され、後から比較できる（新規）
6. THE 計測 SHALL 波及が「発生しない」結果も成果として記録する（新規、軸 A では発生しない見込みであり、ゼロの実証に意味がある）
7. THE 並行数 SHALL 設定で変更できる（新規、同期パス側の需要を動かすため）

### 要件 13: 可観測性

**ユーザーストーリー:** 検証者として、限界に到達した瞬間をグラフで見たい。それにより記事の主張を実測データで裏付けられる。

#### 受入基準

1. THE システム SHALL CloudWatch ダッシュボードで `IteratorAge`、`ConcurrentExecutions`、`Throttles` を可視化する（NFR-3.1）
2. WHEN Lambda 同時実行枠の 80% に到達する THEN システムは Warning アラートを発する（NFR-3.2）
3. WHEN Throttle が発生する THEN システムは Critical アラートを発する（NFR-3.2）
4. THE 各注文の処理フロー SHALL X-Ray でトレースできる（NFR-3.3）
5. THE ダッシュボード SHALL 注文照会 API のスロットルを、後続処理のスロットルと区別して表示する（新規、波及の判定に必要）
6. THE ダッシュボード SHALL DLQ に退避したメッセージ数を表示する（NFR-2.2 の確認）
7. THE ダッシュボード SHALL IaC で定義され、手作業での作成を必要としない（NFR-4.1）
8. THE ダッシュボード SHALL DynamoDB の書き込みスロットルを表示する（新規、テーブル側が壁になっていないことの確認）

### 要件 14: 検証結果の可視化

**ユーザーストーリー:** 検証者として、ブラウザから検証を操作して結果を見たい。それにより CloudWatch と行き来せずに手元で挙動を確かめられる。

#### 受入基準

1. THE フロントエンド SHALL 注文を手動で投入できる（新規）
2. THE フロントエンド SHALL 初期在庫を投入できる（要件 5.7）
3. THE フロントエンド SHALL 負荷生成を開始し、実行状態を表示できる（新規）
4. THE フロントエンド SHALL 注文のステータスと段階ごとの進捗、経過時間を表示できる（新規）
5. THE フロントエンド SHALL 並行計測を実行し、結果（レイテンシ分布、スロットル率）を表示できる（要件 12）
6. THE フロントエンド SHALL 複数回の計測結果を並べて比較できる（新規、シナリオ間の差が本 Spec の成果物）
7. THE フロントエンド SHALL 現在有効な検証パラメータと、実測したシャード数・算出した消費能力を表示する（要件 10.6 / 19）
8. THE 画面 SHALL 在庫管理編から引き継いだブランド要素（アイコン、カラートークン、コンポーネントトークン）を使う（新規、シリーズとしての一貫性）
9. THE 新規機能 SHALL トップページに構築し、サンプルページへのナビゲーションを外す（`.kiro/steering/structure.md` の規約）
10. THE API のベース URL SHALL 環境変数または Amplify の出力から解決し、ハードコードしない（新規）

### 要件 15: スケーラビリティ

#### 受入基準

1. WHILE 投入が消費能力を下回る THE 全後続処理 SHALL 10 秒以内に完了する（NFR-1.1）
2. WHILE 投入が消費能力を上回る THE メッセージ SHALL Streams の保持期限内であれば欠落しない（NFR-1.2 を実測可能な形に調整）
3. THE 後続処理が照会 API に与える影響 SHALL 計測可能である（NFR-1.3）

> **NFR-1.2 を調整した理由:** 出典は「バズピーク時でもメッセージが欠落しない」としているが、
> 滞留が 24 時間分の消費能力を超えればレコードはトリムされ、**欠落する**。
> 欠落しない条件を明示し、欠落までの猶予時間を算出する要件（20.3）に置き換える。

### 要件 16: 信頼性

#### 受入基準

1. THE 全ての後続処理 SHALL 冪等である（二重実行しても結果が変わらない）（NFR-2.1）
2. WHEN 処理が失敗する THEN メッセージは DLQ に退避し、手動またはバッチで再処理できる（NFR-2.2）
3. WHEN バッチ内の一部のレコードが失敗する THEN 他のレコードの処理は継続する（NFR-2.3）
4. THE 冪等性 SHALL Lambda Powertools for TypeScript（Idempotency）で実現する（技術スタック表）
5. THE 冪等キー SHALL 段階ごとに独立させる（新規、段階単位の再実行を可能にするため）
6. THE 冪等性管理テーブル SHALL TTL でレコードを自動失効させる（データモデル定義）
7. THE 業務的な失敗（在庫不足・決済拒否）SHALL 再試行せず終端として扱う（新規、再試行しても結果が変わらずシャードを塞ぐだけ）

### 要件 17: コストとライフサイクル

#### 受入基準

1. THE 全リソース SHALL IaC で管理され、検証終了後に一括削除できる（NFR-4.1）
2. WHILE 通常時である THE アイドルコスト SHALL 最小限である（NFR-4.2）
3. THE DynamoDB テーブル SHALL オンデマンド課金である（データモデル定義）
4. THE 検証全体のコスト SHALL $100 以内に収まる（読み替え5）
5. THE 検証用テーブル SHALL スタック削除時に削除される（新規）
6. THE 検証で生成した注文データ SHALL 蓄積し続けない手段を持つ（新規）
7. THE 各シナリオの実行前 SHALL 想定コストを見積もれる（新規、$100 の枠内で配分を判断するため）
8. WHERE warm throughput の引き上げに課金が発生する THE 検証者 SHALL 実行前にその見積もりを確認できる（新規、下げられない操作であり事前確認が必要）

### 要件 18: 開発体験

#### 受入基準

1. THE IaC SHALL AWS CDK（TypeScript）で記述する（NFR-5.1）
2. THE Lambda ランタイム SHALL Node.js 22.x（TypeScript）である（NFR-5.2）
3. THE デプロイ SHALL `npx ampx sandbox`（開発）または Amplify Hosting（本番）で完結する（読み替え4）
4. THE IaC SHALL `amplify/custom/` に、Lambda SHALL `amplify/functions/` に配置する（読み替え1）
5. THE 変更 SHALL `npm run lint` と `npx tsc --noEmit` を通過する（`.kiro/steering/testing.md` の規約）
6. THE Lambda のコードとフロントエンドのコード SHALL 相互に依存しない（`.kiro/steering/amplify-frontend.md` の規約）

### 要件 19: シャード数と消費能力の実測

**ユーザーストーリー:** 検証者として、各実行時のシャード数を確実に知りたい。それにより消費能力の式が実測と合うかを検証できる。

#### 受入基準

1. WHEN 負荷生成を開始する THEN システムは注文テーブルのオープンシャード数を取得し、実行レコードに記録する
2. THE オープンシャード数 SHALL 終端シーケンス番号を持たないシャードのみを数える
3. THE 実行レコード SHALL 記録したシャード数と設定値（PF、擬似処理時間）から算出した消費能力を含む
4. THE 実行レコード SHALL 実測の処理レートを含み、算出した消費能力と比較できる
5. IF シャード数の取得に失敗する THEN システムは負荷生成を継続し、取得できなかったことを実行レコードに記録する
6. THE シャード数 SHALL 手動のコマンド実行を必要とせずに記録される（新規、全実行を自己記述的にする）

> **なぜ要件にするのか:** シャード数は CloudWatch メトリクスとして提供されない。
> しかし本 Spec の中心的な問いに対する答えが `S × P` に依存するため、
> S が記録されていない実行結果は解釈できない。

### 要件 20: 限界の連鎖の特定

**ユーザーストーリー:** 検証者として、限界がどの順序で現れるかを知りたい。それにより「次に何が壊れるか」を予測できる。

#### 受入基準

1. THE 検証 SHALL 投入が消費能力を超えた時点から滞留が増加することを実測で示す
2. THE 検証 SHALL 滞留の増加率（件/分）を算出できる
3. THE 検証 SHALL 滞留が Streams の保持期限に達してデータが失われるまでの猶予時間を算出できる（要件 15.2）
4. THE 検証 SHALL 投入を停止した後、滞留を消化しきるまでの回復時間を実測できる
5. THE 検証 SHALL 各シナリオで「壁になった要素」と「壁にならなかった要素」を区別して記録する
6. THE 検証 SHALL シャード数を増やした構成（軸 B）で、壁が `S × P` から別の要素へ移るかを実測する
7. WHERE 壁が Lambda の同時実行枠へ移った THE 検証 SHALL 同期パスへの波及が発生するかを実測する
8. THE 検証 SHALL 消費能力の式（`S × P ÷ D`）が実測と一致するか、乖離があるならその要因を記録する

## 検証シナリオ

投入レートは絶対値で刻む。基準値の曖昧さを避けるため（前提の末尾を参照）、
「何倍のバズ」ではなく「壁の位置」を測る。

消費能力の想定は `S × P ÷ D`。以下の表は S = 4（推定）での値であり、
**実測値で置き換える**（要件 19）。

### 軸 A: 既定のオンデマンドテーブル

| ID | 投入 | PF | D | 想定能力 | 狙い |
|----|------|----|---|---------|------|
| A0 | 2/分 | 1 | 3.6s | 67/分 | 基準。シャード数の実測、end-to-end 遅延、要件 15.1 の確認 |
| A1 | 60/分 | 1 | 3.6s | 67/分 | 壁の直前。まだ耐えることを確認 |
| A2 | 200/分 | 1 | 3.6s | 67/分 | **1 つ目の壁を超える。** 滞留の増加率を測る |
| A3 | 200/分 | 10 | 3.6s | 667/分 | PF を上げれば解消するかを確認 |
| A4 | 1,000/分 | 10 | 3.6s | 667/分 | **2 つ目の壁を超える。** PF の上限（10）に達した状態 |
| A5 | 2,000/分 | 10 | 3.6s | 667/分 | 限界の先。データロス猶予時間を算出 |
| A6 | 1,000/分 | 10 | 0.1s | 24,000/分 | **D を縮めて式を検証。** 3 変数のうち D だけを動かす |
| A7 | A4 停止後 | 10 | 3.6s | 667/分 | **回復時間の実測。** 滞留の消化にかかる時間 |
| A8 | A4 + 並行計測 | 10 | 3.6s | 667/分 | 同期パスへの波及の有無（**発生しない見込み。ゼロの実証**） |

### 軸 B: 事前ウォームでシャードを増やしたテーブル

| ID | warm WCU | 投入 | PF | 狙い |
|----|---------|------|----|------|
| B0 | 既定 | — | — | ウォーム前のシャード数を記録（軸 A のベースライン） |
| B1 | 40,000 | 2/分 | 10 | **仮説検証: ウォームでシャードが増えるか。** 増えなければ軸 B はフォールバックへ |
| B2 | 40,000 | 2,000/分 | 10 | 軸 A で壁だったレートが通るかを確認 |
| B3 | 100,000 | 16,000/分 | 10 | **同時実行枠に到達するか。** 次の壁の特定 |
| B4 | 100,000 | 16,000/分 + 並行計測 | 10 | **巻き添えが自然に発生するか。** 軸 A の A8 との対比 |

B1 が軸 B 全体の前提である。ウォームスループットとシャード数の関係は
AWS ドキュメントに明記されていないため、**検証すべき仮説**として扱う。
B1 が否定された場合のフォールバックは design で定める。

シナリオ F〜K（SQS ファンアウト、FIFO / Pipes / Kinesis）は本 Spec のスコープ外。

## Phase 2 に向けた拡張点

本 Spec では作らないが、後続 Spec（SQS ファンアウト）で必要になることが分かっている箇所。
**先回りして実装はしない**が、design では変更が波及する範囲を明示しておく。

| 項目 | 本 Spec での扱い | Phase 2 で必要になること |
|------|----------------|----------------------|
| パイプライン構成の切り替え | 作らない。`direct` のみ | 環境変数による切り替えと、選択されていない構成のリソースを作らない制御 |
| `pipeline_mode` 属性 | 常に `direct` を記録する | `fanout` を記録し、両構成の計測結果を見分ける |
| ステータス更新の並列安全性 | 不要（直列実行のため素朴な更新でよい） | 4 ワーカーの並列完了でステータスが巻き戻らない仕組み |
| 決済の流量制御（FR-2.5） | 満たせないことを記録する | ワーカーごとの同時実行数上限による流量制御 |
| 段階ごとの冪等キー | 段階ごとに独立させる（要件 16.5） | そのまま流用できる |
| 段階ごとの進捗属性 | 経過時間の計測のために持つ（要件 8） | そのまま流用できる |
| シャード数の記録 | 実行レコードに自動記録（要件 19） | そのまま流用できる。ルーター Lambda の並列度の解釈に必要 |
| 壁の所在 | `S × P`（軸 A）/ 同時実行枠（軸 B） | ルーターが SQS に逃がすため `S × P` はスループットの壁でなくなる。**同時実行枠が主戦場になる** |

軸 B で同時実行枠の壁を先に測っておくと、Phase 2 の
「ファンアウトで解放されたスケールが、次にどこで止まるか」の予測ができる。
