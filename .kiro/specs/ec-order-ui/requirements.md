# Requirements Document

EC 注文画面のリニューアル（ec-order-ui）

## Introduction

Kiro Roasters の検証ダッシュボードの「注文」タブを、**顧客が使う EC らしい画面**に作り直す。
現状の注文タブは `POST /orders` を直接叩く API 操作コンソールの見た目で、
商品を 1 行ずつプルダウンで選ぶ・顧客 ID を手入力する・初期在庫の投入が同じ画面に並ぶ、
という検証者向けの構成になっている。

これを商品グリッド → カート → 注文 → 状況表示という EC の導線に変える。
目的は 2 つ。

1. 技術記事で「Web 画面でこう操作すると裏でこうなる」を見せる導線にする。
   顧客の画面が EC らしく見えることで、裏の非同期パイプラインの壊れ方
   （画面は「処理中」なのに滞留している）との対比が効く。
2. 検証操作（初期在庫の投入、顧客 ID 指定、ランダム生成）を顧客画面から分離し、
   運用者向けの操作として設定タブへ寄せる。

**本 Spec は UI の再構成が主で、注文処理パイプライン（`order-accept` / `order-processor` /
Streams）のロジックは変更しない。** 商品マスタ（`catalog.ts`）には表示用の属性を追加するが、
SKU 形式・価格・注文処理には影響させない。

### 背景

- 商品マスタは `amplify/functions/shared/catalog.ts` で 10 産地 × 6 焙煎度 × 4 容量 = 240 SKU を生成する。
  現状 `GET /catalog` が返すのは `sku` / `name` / `price` の 3 項目のみ。
- 産地で絞り込む UI を素直に作るため、`GET /catalog` に産地・焙煎度・容量を持たせる（案 Y）。
  フロントが SKU 文字列を切り出して産地を推定する方式（案 X）は採らない。
- 画面幅は現状 `--max-width: 960px`。商品グリッドを並べるため 1120px に広げる。

## スコープ

### 含む

- `catalog.ts` の商品に `origin` / `roast` / `size`（表示名）を追加し、`GET /catalog` で返す
- フロント `types.ts` の `CatalogProductView` に同項目を追加
- 注文タブを商品グリッド + 産地絞り込み + カート + 注文 → 状況表示に再構成
- 初期在庫の投入 UI を設定タブへ移設
- 顧客 ID 手入力・ランダム生成チェックボックスを UI から削除
- 画面幅 960 → 1120px

### 含まない

- 注文処理パイプライン（`order-accept` / `order-processor` / Streams）のロジック変更
- 負荷テストタブ・計測結果タブの変更
- 商品画像の追加（産地に応じた色 + アイコンのプレースホルダで代用）
- 認証の追加（PoC のまま、API Gateway は認証なし）
- SKU 形式・価格計算・ポイント計算の変更

## Glossary

| 用語 | 定義 |
|------|------|
| 商品グリッド | 商品をカード状に並べる一覧。産地で絞り込める |
| カート | 注文前に選んだ明細を保持する画面上の状態。API には送らない |
| 産地 | コーヒー豆の産地（エチオピア、ブラジル等）。`catalog.ts` の `ORIGINS` に対応 |
| 検証操作 | 初期在庫の投入・顧客 ID 指定・ランダム生成など、顧客ではなく検証者が使う操作 |

## Requirements

### 要件 1: 商品マスタの表示用属性

**ユーザーストーリー:** 開発者として、産地や容量で商品を絞り込みたい。
そのために商品マスタが表示用の属性を返してほしい。

#### 受入基準

1. WHEN `GET /catalog` が呼ばれた THEN 各商品は `sku` / `name` / `price` に加えて `origin` / `roast` / `size` を含む
2. `origin` は産地の表示名（例: `エチオピア イルガチェフェ G1`）とする
3. `roast` は焙煎度の表示名（例: `ミディアム`）とする
4. `size` は容量の表示名（例: `200g`）とする
5. IF `catalog.ts` の SKU 生成ロジックが変わった THEN 追加属性も同じ組み合わせから導出され、SKU と矛盾しない
6. 追加属性は表示専用であり、SKU 形式・価格・注文処理には影響しない
7. WHEN フロントの `CatalogProductView` を参照する THEN `origin` / `roast` / `size` が型として利用できる

### 要件 2: 商品グリッドと絞り込み

**ユーザーストーリー:** 顧客として、商品を一覧から選びたい。240 件すべてではなく、
産地で絞って探したい。

#### 受入基準

1. WHEN 注文タブを開いた THEN 商品がカード状のグリッドで表示される
2. 各カードは商品名・産地・焙煎度・容量・価格を表示する
3. 各カードは商品画像の代わりに産地に応じた色とアイコンのプレースホルダを表示する
4. WHEN 産地の絞り込みを選んだ THEN その産地の商品だけが表示される
5. WHEN 絞り込みを「すべて」にした THEN 全商品が表示される
6. IF 商品マスタの取得に失敗した THEN エラーを表示し再取得の手段を提供する
7. WHILE 商品マスタを読み込み中 THE UI は読み込み中であることを示す
8. 各カードには「カートに追加」の操作がある

### 要件 3: カート

**ユーザーストーリー:** 顧客として、選んだ商品をまとめて確認してから注文したい。

#### 受入基準

1. WHEN カードの「カートに追加」を操作した THEN その商品がカートに入る
2. IF 同じ商品を再度追加した THEN 数量が増える（明細は重複しない）
3. WHEN カート内の数量を変更した THEN 合計金額と獲得予定ポイントが再計算される
4. WHEN カート内の明細を削除した THEN その明細がカートから消える
5. カートは合計金額と獲得予定ポイントを表示する
6. IF カートが空 THEN 注文の操作は無効化される
7. カートの明細は既存の注文明細検証（`buildOrderDraft`）に渡せる形式である
8. WHERE 数量が上限（`MAX_ITEM_QTY`）を超える THE UI は送信前に気づけるようにする

### 要件 4: 注文と状況表示

**ユーザーストーリー:** 顧客として、カートの内容で注文し、その後の状況を確認したい。

#### 受入基準

1. WHEN 「この内容で注文する」を操作した THEN カートの明細で `createOrder` を呼ぶ
2. WHEN 注文が成功した THEN 注文番号と受付結果（ステータス・合計・受付時刻）を表示する
3. WHEN 注文が成功した THEN その注文 ID を状況表示（`OrderStatusPanel`）に引き継ぐ
4. WHEN 注文が成功した THEN カートは空になる
5. IF 注文が失敗した THEN 失敗内容を表示し、カートの内容は保持する
6. WHILE 注文の送信中 THE 注文の操作は無効化される
7. 顧客 ID は画面から指定せず、API のデフォルト（テスト顧客の自動割り当て）に委ねる
8. 注文明細は画面で指定した内容のみとし、ランダム生成の選択肢は設けない

### 要件 5: 検証操作の設定タブへの移設

**ユーザーストーリー:** 検証者として、初期在庫の投入を運用操作として設定タブで行いたい。
顧客画面には出したくない。

#### 受入基準

1. WHEN 設定タブを開いた THEN 初期在庫の投入 UI が利用できる
2. 初期在庫の投入は現状の機能（在庫数の指定、`POST /inventory/seed`、結果表示）を維持する
3. WHEN 注文タブを開いた THEN 初期在庫の投入 UI は表示されない
4. WHEN 注文タブを開いた THEN 顧客 ID の入力欄・ランダム生成のチェックボックスは表示されない
5. 移設後も設定タブの既存表示（検証パラメータ、消費能力の見積もり）は維持される

### 要件 6: レイアウトと外観

**ユーザーストーリー:** 開発者として、EC らしい見た目にしたい。既存のデザイントークンと
アクセシビリティを保ちたい。

#### 受入基準

1. WHEN ダッシュボードを表示した THEN 全体の最大幅は 1120px である
2. 商品カード・カート・ボタンは既存のデザイントークン（`globals.css` の CSS 変数・
   コンポーネントクラス）を使い、生の色値を書かない
3. 商品グリッドは画面幅に応じて列数が変わる（レスポンシブ）
4. WHEN キーボードで操作する THEN 商品の追加・カート操作・注文がキーボードだけで完結する
5. 非同期の結果（注文の成否、商品マスタの読み込み）は支援技術に伝わる（`aria-live` 等）
6. タブ構成（注文 / 負荷テスト / 計測結果 / 設定）は維持する

## 非機能要件

1. `npm run lint` と `npx tsc --noEmit` が通る
2. UI ロジックとインフラ処理の分離を保つ（`src/lib/orders/` の API クライアント・算術は変更しない）
3. 既存の API クライアント（`api.ts`）と注文明細検証（`order-form.ts`）を再利用し、重複実装を作らない
4. バックエンド変更（`catalog.ts` / catalog ルート）はフロントへの影響を design で説明する
5. Amplify sandbox での反復開発と相性の良い、段階的な変更にする

## デプロイへの影響

- `catalog.ts` と catalog ルートの変更は**再デプロイ**が必要（`GET /catalog` の応答形状が変わる）。
- 注文処理パイプライン・テーブル定義・IAM は変更しないため、既存の実測結果（`docs/poc/`）への影響はない。
- フロントのみの変更（グリッド・カート・幅）は Amplify Hosting の再ビルドで反映される。
