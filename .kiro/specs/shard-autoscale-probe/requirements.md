# Requirements Document

シャード自動拡張プローブ — 緩やかな負荷漸増でオープンシャード S はどう育つか（+ 各段の IteratorAge 実測）

## Introduction

既定のオンデマンド DynamoDB テーブルに **Lambda トリガ（DynamoDB Streams イベントソース）を繋いだ
最小構成**を使い捨てで用意し、**警告的なバズではなく緩やかに増えていく書き込み負荷**をかけたとき、
オープンシャード数 **S** が初期 4 からどう育つか、そして各負荷段で **IteratorAge（滞留遅延）**が
どの程度になるかを実測する検証セットを定義する。

この Spec は **検証を回せる状態まで**を対象とする（本番運用・常時稼働・オンライン公開は対象外）。

### 背景（直前までの実測で確定していること）

[docs/poc/shard-warm-throughput-experiment.md](../../../docs/poc/shard-warm-throughput-experiment.md)
の E1〜E6 で次を実測済み。

- オープンシャード数 S は **warm/WCU の設定値で決定論的**に決まる。負荷・過負荷（48MB/s）・
  データ量（3.6GB）・項目サイズ（64KB）はいずれも S を動かさない。
- オンデマンド warm **4,000 → S = 4**、warm **40,000 → S = 64**（下限 ÷1,000 の 1.6 倍）。
- プロビジョンドは同じ 40,000 で S = 41（下限の約 1.0 倍）。かつ Stream 有効テーブルは
  オンデマンド/プロビジョンドとも **WCU 40,000 が上限**（真の律速は Streams write クォータ
  `L-923BEB7A`）。
- Lambda 同時実行の上限 `= S × P`。**D（1 レコード処理時間）は上限に入らない**（D は滞留と
  スループットに効く）。

### 中心的な問い

> **既定のオンデマンドテーブル（S=4, warm 4,000）を、設定を一切いじらずに緩やかな書き込み漸増で
> 育てたとき、S は段階的に増えるのか。どこまで育つのか。各段での遅延（IteratorAge）はどの程度か。**

事前仮説（E1〜E6 と公式仕様から）:

1. オンデマンドは「直近ピークの 2 倍」を追従して自動スケールし、分割は不可逆に残る。
   → **S は 4 から段階的に増える**（成り立つ見込み）。
2. 到達した書き込みピークが warm として残り、S はそのピークに対応する値になる。
   → ピークが 40,000 write/s まで育てば **S = 64 に収束**。40,000 がクォータ上限ゆえ
   **自動拡張だけで到達できる S の天井も 64**（条件付きで成り立つ見込み）。
3. D=3 秒を固定し投入レートを上げるほど、同時実行 `S×P` が埋まり IteratorAge が増える。

これらは実測で検証・反証する対象であり、確定事実として扱わない。

### この検証を忠実版ではなく圧縮版で行う理由（途中段打ち切り + 終点外挿）

**終点 S は既知である。** E1〜E6 で「warm/WCU 40,000 → S=64 が Max 固定」と確定済み。
したがって本検証は Max（40k = S64）まで実測せず、**低〜中レートの途中段までを S が安定するまで
丁寧に実測し、S の成長カーブの形を取る**。最終到達点（S=64）はカーブからの**外挿で確認**する。

- 各段は時間固定ではなく **S（オープンシャード数）が安定するまで待ってから**次段へ進む
  （「負荷追従で分割が完了したこと」を確認してから次に行く）。
- 上げる上限は **16,000 write/s（4 段目）まで**。初期 S=4 を含め 4〜5 点でカーブを引く。
- カーブが規則的（線形等）なら、既知の終点 S=64 と突き合わせて全体像を確定する。
- 圧縮版の限界: 「30 分以上の緩やか漸増」ではないため段切替直後にスロットリングが混じりうる。
  実効レート低下として記録する。

### D の確定

D = **3 秒**。過去の軸 A / 軸 B 検証（D≈3.6s / D≈0.7s）と比較可能で、かつ低レートでも
IteratorAge（滞留遅延）が観測しやすいため。切りよく 3.0 秒ちょうどに固定する。

## Glossary

| 用語 | 定義 |
|------|------|
| S | オープンシャード数（`EndingSequenceNumber == null` の Stream シャード数）。並列読み出し能力の指標 |
| P | ParallelizationFactor。1 シャードあたりの Lambda 並列度（イベントソースマッピング設定） |
| D | 1 レコードあたりの処理時間。本検証では 3.0 秒に固定 |
| IteratorAge | `GetRecords.IteratorAgeMilliseconds`。レコードが Stream に書かれてから消費されるまでの遅延 |
| 負荷段 | 投入目標レートの 1 段階（例 2k → 4k → 8k → 16k → 32k → 40k write/s を目標とする各ステップ）|
| 検証スタック | 本 Spec で作る使い捨ての最小構成（テーブル + Stream + 消費 Lambda + ESM + IAM + ドライバ + 計測）|

## Requirements

### 要件 1: 使い捨ての検証スタック（テーブル + Stream + 消費 Lambda）

**ユーザーストーリー:** 検証者として、既定オンデマンドの DynamoDB テーブルに Lambda を繋いだ
最小構成を使い捨てで用意したい。S の育ちと IteratorAge を同一環境で観測するため。

#### 受入基準

1. WHEN 検証スタックを作成する THEN システムは **PAY_PER_REQUEST・単一ハッシュキー（pk:S）・
   GSI なし・Streams NEW_AND_OLD_IMAGES 有効**の DynamoDB テーブルを 1 つ作成すること（新規）
2. WHEN テーブルを作成した直後 THEN warm write は既定の **4,000**、S は **4** であることを計測で確認すること（新規）
3. WHEN 消費 Lambda を用意する THEN その Lambda は 1 レコードあたり **D = 3.0 秒の単純 sleep**を
   行うこと（本検証では決済等の擬似処理は行わず sleep 固定）（新規）
4. WHEN Lambda を Stream に繋ぐ THEN DynamoDB Streams イベントソースマッピング（ESM）を作成し、
   **ParallelizationFactor（P）を明示設定**すること（既定は要件 2 で確定）（新規）
5. IF 検証スタックが PoC 本体（Amplify / sandbox）の構成に副作用を与える THEN それは不合格とする。
   検証スタックは **CLI またはスタンドアロンのツールで単独作成**し、`src/` `amplify/` `agents/` を
   変更しないこと（steering: structure 準拠）（新規）
6. WHERE 検証リソースを作る THE SYSTEM SHALL リージョンを **us-west-2** とし、名前に
   `shard-autoscale-probe` 由来の識別子を付けて既存リソースと区別できるようにすること（新規）
7. WHEN 検証スタックを実装する THEN **作成 → 実行 → お片付けの流れを README で明示できる**
   方式（単一の CLI スクリプト一式。例: `create` / `run` / `teardown` を各 1 コマンドで実行し、
   手順を README に列挙できる）を採用すること。CDK/SAM は採用しない（README での
   create→teardown の見通しと手軽さを優先）（新規）

### 要件 2: 負荷段の設計（緩やかな漸増）

**ユーザーストーリー:** 検証者として、バズ的な一発ではなく段階的に上がる投入レート列を定義したい。
現実の「緩やかに負荷が増える」状況を圧縮して再現するため。

#### 受入基準

1. WHEN 負荷段を定義する THEN 投入目標レートを **4 段で単調増加**に並べること。
   列は **2k → 4k → 8k → 16k write/s**（1〜3 段は前段の 2 倍 = オンデマンドの「直近ピークの
   2 倍追従」境界を踏む。4 段目 16k で**打ち切る**。Max=40k/S64 は既知のため実測しない）とすること（新規）
   - 投入側は複数プロセス並列（`overload.mjs` 相当）で目標レートに合わせる。各段の必要
     プロセス数の目安（約 7k write/s ÷ プロセス）: 2k=1 / 4k=1 / 8k=2 / 16k=3。
   - 8 プロセスで ~48k 到達実績があるため 16k は余裕。**実効到達レートが S の上限を規定する**ため
     各段の実効レートを必ず記録すること（新規）

2. WHEN 各段を実行する THEN **S が安定するまで**（オープンシャード数が **3 分間変化しない**ことを
   もって安定とみなす）負荷を継続し、安定を確認してから次段へ進むこと。ただし暴走防止に
   **1 段あたり最大 10 分**で打ち切ること（時間固定ではなく S 安定ゲート）（新規）

3. WHERE P（ParallelizationFactor）を固定する THE SYSTEM SHALL 全段を通じて **P = 10 固定**で
   実行すること（軸 B と揃える。本検証では P は変数にしない）（新規）
4. IF 投入側（単一プロセス）が目標レートに達しない THEN E2/E6 で用いた**複数プロセス並列**
   （`overload.mjs` 相当）で合算レートを稼ぐこと。到達した実効レートを段ごとに記録すること（新規）
5. WHEN 各段の負荷を生成する THEN キーは**乱数プレフィックス + ULID で全キースペースに分散**し、
   ホットパーティションを避けること（E2 と同じ方式）（新規）

### 要件 3: 各段での S 計測（自動拡張カーブの観測）

**ユーザーストーリー:** 検証者として、各負荷段でオープンシャード S を数え、4 からどう育つかの
カーブを得たい。「段階的に S が増える／中間ピークで中間 S／最終的に S=64 収束」を検証するため。

#### 受入基準

1. WHEN 各段の負荷が落ち着いた THEN **オープンシャード S を計数**し、段・目標レート・実効レートと
   対応づけて記録すること（ページング込み、`count-shards.mjs` 相当）（新規）
2. WHEN S を記録する THEN 併せて warm write 表示値・TOTAL シャード数・計測時刻を残すこと（新規）
3. WHEN 全段を終えた THEN **(実効到達ピーク write/s, S)** の対応列を 1 つの表／カーブとして
   まとめること（新規）
4. IF 最終段（目標 40k）で S が 64 に達した THEN 仮説 2（S=64 収束）を支持と判定すること。
   IF 64 未満で頭打ち THEN 到達ピークが 40k に届かなかったか別要因かを切り分けて記録すること（新規）
5. WHERE S が前段から増えた THE SYSTEM SHALL その増加が**どの投入ピーク更新に対応したか**を
   可能な範囲で紐づけること（オンデマンド「直近ピークの 2 倍」追従の確認）（新規）

### 要件 4: 各段での IteratorAge（遅延）実測

**ユーザーストーリー:** 検証者として、各段で IteratorAge を観測し「実際どれくらいの遅延になるか」の
指標を得たい。S・レート・D=3s の組み合わせが遅延に与える影響を知るため。

#### 受入基準

1. WHEN 各段で負荷をかけている間 THEN 消費 Lambda の **`GetRecords.IteratorAgeMilliseconds`**
   を CloudWatch から取得し、段ごとに代表値（最大・p95・平均のいずれか以上）を記録すること（新規）
2. WHEN IteratorAge を記録する THEN 同じ段の **S・実効レート・同時実行数（可能なら `ConcurrentExecutions`）**
   と並べ、`S × P ÷ D` の理論処理能力に対する充足度と対応づけること（新規）
3. IF ある段で投入レートが処理能力 `S × P ÷ D` を超える THEN IteratorAge が時間とともに増加
   （滞留）することを観測・記録すること（新規）
4. IF ある段で投入レートが処理能力の範囲内 THEN IteratorAge が低位で安定することを観測・記録すること（新規）
5. WHEN D を扱う THEN **D = 3.0 秒**で固定し、D は本検証では変数にしないこと（新規）

### 要件 5: 後片付けとコスト管理（最重要の運用制約）

**ユーザーストーリー:** 検証者として、検証後に課金源を確実に止めたい。warm は不可逆で、放置すると
課金が続くため。

#### 受入基準

1. WHEN 検証が完了した THEN 検証スタックの**全リソース（テーブル・ESM・Lambda・IAM ロール等）を削除**
   すること。削除後に残存が無いことをリスト照会で確認すること（新規）
2. IF warm を引き上げたテーブルが検証中に生じた THEN それは不可逆のため、検証後**必ず削除**すること（新規）
3. WHILE 検証を実行している THE SYSTEM SHALL 想定外に高額化しうる操作（長時間の高レート投入放置、
   消し忘れ）を避け、各段は数分で切り上げること（steering: security／コスト判断は都度ユーザーに仰ぐ）（新規）
4. WHEN コストが発生する操作を行う THEN 事前に概算を提示し、ユーザーの判断を仰ぐこと
   （「コストを理由に止めない。判断を仰ぐ」方針）（新規）

### 要件 6: 記録と再現性

**ユーザーストーリー:** 検証者として、結果と手順を既存の検証記録に沿って残したい。後から再現・
引用できるようにするため。

#### 受入基準

1. WHEN 検証を終えた THEN 結果を **`docs/poc/`** 配下に、E1〜E6 の記録と同じ記法
   （S/P/D 記号・実測表・🟢/🔴 判定）でまとめること（新規）
2. WHEN 使い捨てスクリプトを置く THEN **`tmp/`（git 管理外）**に置き、リポジトリ主要ディレクトリを
   汚さないこと（既存 `.gitignore` の `tmp/` を踏襲）（新規）
3. WHEN 検証スタックの定義を残す THEN 再現可能な形（CLI 手順 or スタンドアロン IaC スニペット）で
   記録すること。ただし PoC 本体の `amplify/` には混ぜないこと（steering: structure 準拠）（新規）
4. IF 本検証の結論が E1〜E6 の結論（S は warm 決定論・1,000 多重には Streams クォータ引き上げが必要）に
   影響する THEN その関係を明記すること（新規）

## 非機能・制約（横断）

- **NFR-圧縮版の限界:** 各段は数分で上げるため「30 分以上かけた緩やか漸増」ではない。
  30 分ルール違反によるスロットリングが混入しうる点を結果に明記する。
- **NFR-分離:** 検証スタックは PoC 本体（Amplify sandbox / `src` / `agents`）と完全分離。
- **NFR-リージョン:** us-west-2 固定。Lambda はオレゴンで常用が無く、同時実行枠 1,000 を
  本検証 Lambda がほぼ独占できる前提。
- **NFR-可観測性:** S は DescribeStream、IteratorAge と ConcurrentExecutions は CloudWatch から取得。
- **NFR-セキュリティ:** 認証情報をハードコードしない。IAM ロールは最小権限（Stream 読み取り + ログ出力）。

1. 消費 Lambda の実装詳細（**単純 sleep 3 秒**は確定。ランタイム・メモリ・バッチサイズ・
   `MaximumBatchingWindow` 等の ESM 詳細は設計で確定）。
2. 負荷段は **S 安定ゲート（3 分変化なしで安定・1 段上限 10 分）**で進む（確定）。
3. 計測の具体: **IteratorAge の代表値**（最大/p95/平均）と取得間隔、`ConcurrentExecutions` の取得方法。
4. S が各投入ピーク更新にどう対応したかを**時刻で紐づける**方法（CloudWatch 時系列との突き合わせ）。

### 設計フェーズ入力時点で確定済み

- D = 3.0 秒（単純 sleep） / P = 10 固定 / レート列 **4 段（2k→4k→8k→16k で打ち切り）** / 終点 S=64 は外挿
- 作り方 = 単一 CLI スクリプト一式（create / run / teardown、README で手順明示）
- リージョン = us-west-2 / 課金モード = 既定オンデマンド（warm 4,000 スタート）
